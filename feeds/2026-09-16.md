**🔄 21:27 👤 @paulox забустил пост от @GitRon@mastodon.social**
💬 Most [#Django](https://mastodon.social/tags/Django) projects have too many apps.

An app is not a unit of code organisation – it's a namespace in your database. Every label lands in migrations, content types, FK strings. Expensive to move. Python packages are free.

So: start with one app. Split by domain, never per model. A few satellites that never import a domain (import-linter in CI). One `common`, not `common` and `utils`.

Wrote up what we've learned, counterexamples welcome:

[https://medium.com/ambient-innovation/1001-django-apps-the-myth-of-a-well-structured-django-project-f3d62f120331](https://medium.com/ambient-innovation/1001-django-apps-the-myth-of-a-well-structured-django-project-f3d62f120331)

💬 Today it's been exactly as many days from Python 0.9.1 (Feb 20, 1991) to Python 3.0.0 (Dec 3, 2008) as there have been from Python 3.0.0 to now!

import datetime as dt

when_091 = dt.date(1991, 2, 20)
when_300 = dt.date(2008, 12, 3)
today = dt.date(2026, 9, 16)

days_091_300 = (when_300 - when_091).days
days_300_now = (today - when_300).days

print(f"{days_091_300} days from 0.9.1 to 3.0.0")
print(f"{days_300_now} days from 3.0.0 to now")
