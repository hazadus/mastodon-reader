**🕒 05:12 👤 @devto@www.urbanmind.net**
💬 Introduction

Most backend services own state. They write to a database, track sessions, remember where you are in a flow.

StareBrain’s backend does none of that. Every request to /next-step is self-contained. The backend reads what the client sends, decides the next action, and returns it. Nothing is written. Nothing is stored. The session ends when the response leaves.

This is a deliberate architectural choice — and it has real consequences for how the agent handles plans, step history, and recovery.

 The Request and Response

The full schema for a single agent step:

`class AgentStepRequest(BaseModel):
 task: str
 screen_description: str
 current_package: Optional[str] = None
 steps_so_far: list[str] =
[] step_count: int
 known_facts: str = ""
 plan: list[str] =
[] current_subgoal: int = 0
 screenshot_b64: Optional[str] = None
 capabilities: list[str] =

[]class AgentStepResponse(BaseModel):
 reasoning: Optional[str] = None
 action: str
 target_index: Optional[int] = None
 text_to_type: Optional[str] = None
 app_name: Optional[str] = None
 setting_name: Optional[str] = None
 status_text: str
 final_answer: Optional[str] = None
 remember: Optional[RememberFact] = None
 plan: Optional[list[str]] = None
 advance_subgoal: bool = False
 replan: Optional[list[str]] = None
 requires_confirmation: bool = False
 confirmation_reason: Optional[str] = None
 question: Optional[str] = None
 options: Optional[list[str]] = None`

Notice what’s in the request: steps_so_far, plan, current_subgoal, known_facts. The client sends the entire history of the session on every call. The backend never looks anything up — it receives the full context and decides from that alone.

 Why Stateless

Three reasons drove this decision:

1. The client already has the state.
The Android app is executing actions, reading screens, tracking what happened. It has the most accurate picture of session state by definition. Duplicating that in a backend database adds a consistency problem: which one is right when they diverge?

2. Resumability is free.
If the backend crashes mid-session, the client resumes by sending the same request again. There’s no session to recover, no checkpoint to restore. The next call picks up exactly where the last confirmed step left off.

3. Scaling is trivial.
A stateless backend has no affinity — any instance handles any request. No sticky sessions, no shared cache, no distributed state to synchronize.

 What the Client Owns

Because the backend is stateless, the client is the source of truth for:

`data class AgentSession(
 val task: String,
 val stepsSoFar: MutableList<String>,
 val plan: MutableList<String>,
 val currentSubgoal: Int,
 val knownFacts: String,
 val stepCount: Int
)`

After each response, the client updates its local session and sends the updated state on the next call. The backend never needs to remember the previous step — it’s in the request.

 Plan and Replan

The response can carry a plan (initial plan, set on the first step) or a replan (replacement plan mid-session). The client applies whichever arrives:

`fun applyResponse(session: AgentSession, response: AgentStepResponse) {
 response.plan?.let { session.plan.addAll(it) }
 response.replan?.let {
 session.plan.clear()
 session.plan.addAll(it)
 }
 if (response.advance_subgoal) {
 session.currentSubgoal += 1
 }
 response.remember?.let {
 session.knownFacts += "\n${it.key}: ${it.value}"
 }
 session.stepsSoFar.add(response.action)
 session.stepCount += 1
}`

The backend proposes. The client applies and owns. On the next request, the updated plan goes back up in AgentStepRequest.plan.

 The Tradeoff

Stateless is not free. The request payload grows with session length — steps_so_far and known_facts accumulate. Long sessions send more data per call.

The mitigation: steps_so_far is summarized rather than appended verbatim after a threshold, and known_facts is structured as key-value pairs so the backend can read the relevant facts without parsing a growing narrative.

The other tradeoff: if the client loses state (app killed, device rebooted mid-task), the session is gone. There’s no server-side recovery. For the current use case — short agentic tasks on a mobile device — this is acceptable. For long-running tasks that span hours, it would need rethinking.

💬 I compared django-bolt and django-ninja today. Bolt is 1.6 to 1.7x faster on real database endpoints.

The catch: Bolt decides where to run a sync handler by scanning its source code for ORM calls. If your query is hidden inside a function call, like `return services.get_order(id)`, Bolt won't see it. The query runs on the only worker thread, and every other request waits.

Async handlers fix this.

💬 Live stream chat is deceptively hard. What starts as "just broadcast messages to connected clients" becomes a distributed systems problem the moment you scale past a single server instance.

Wapi is a live streaming app tailored for African content, with a backend written in Go. Its chat takes a pragmatic approach to scaling: an in-memory WebSocket hub per process, with an optional Redis Pub/Sub broadcaster for cross-instance fan-out. In this post I'll break down why the design works, what it costs you, and where it starts to strain.

 The Problem With Single-Instance Chat

If you only ever run one backend instance, keeping all connected clients in memory and broadcasting to them directly is the simplest and fastest option. You get low latency, no external dependencies, and a system that is easy to reason about. Go is well suited to this because goroutines and channels make managing thousands of concurrent connections cheap.

In production, though, you'll almost always want multiple instances behind a load balancer, for redundancy, for rolling deploys, and for capacity. With a pure in-memory hub, a client connected to instance A never receives messages sent by a client connected to instance B. Your "live" chat fragments based on which instance each user was routed to, and users in the same stream see different conversations.

 Why Not Just Use Sticky Sessions?

The obvious shortcut is to route every viewer of a given stream to the same instance. It can work, but it has real drawbacks:

Hot streams break it. A popular stream can have more viewers than a single instance can hold, and you can't split it.Deploys get painful. Restarting an instance drops every connection pinned to it, and all those clients reconnect at once.Load balancing gets complicated. You need routing logic that understands stream IDs, not just connections.Fan-out between instances removes all three problems. Any instance can serve any viewer, and the instances keep each other informed.

 The Architecture

The design is a hybrid. Each instance runs its own hub that manages WebSocket connections and broadcasts locally. If REDIS_URL is configured, each instance also publishes its messages to Redis and subscribes to messages from other instances. A message arriving from Redis is re-broadcast to local connections, but only if it originated on a different instance, so it never echoes back.

This gives you:

Local speed: no network hop between clients on the same instanceHorizontal scalability: add instances without breaking chatGraceful degradation: without Redis, it falls back to single-instance modeSimplicity: no dedicated message queue, just Redis Pub/Sub

 How the In-Memory Hub Works

The hub's job is to track which clients are watching which stream, and to deliver each message to everyone watching that stream. Internally it is a map from stream ID to a set of connected clients.

The important design choice is how that map is protected. Instead of guarding it with locks, the hub runs in a single goroutine and receives all changes through channels: one for clients registering, one for clients leaving, and one for messages to broadcast. Because only that goroutine ever touches the map, there are no data races and no lock contention, and the event loop is easy to follow.

Each client gets its own buffered outbound channel, drained by a dedicated write goroutine that pushes messages down the WebSocket. A matching read goroutine handles incoming messages. This read/write pump pair per connection is the standard pattern for WebSockets in Go, and it keeps slow network writes off the hub's critical path.

 The Slow Client Problem

Every real-time system eventually meets the slow consumer: a client on a bad mobile connection whose outbound buffer fills up. If the hub blocks while delivering to that client, one bad connection stalls chat for everyone in the stream.

For an audience that is largely on mobile data, this isn't an edge case, it's the normal case.

The fix is to never block. If a client's buffer is full, the hub drops that client, closes its channel, and lets the client reconnect. It sounds harsh, but it protects the many from the few. Combined with history loading on reconnect, the user barely notices.

 Adding Redis for Cross-Instance Fan-Out

On startup, each instance generates a unique instanceID, for example with uuid.NewString(). When it publishes a message to Redis, it attaches this ID to the payload. When it receives a message from Redis, it checks the ID first:

Same ID: the message came from this instance, and local clients already got it directly from the hub. Ignore it.Different ID: another instance produced it. Hand it to the local hub for delivery.Without that check, every message would be delivered twice on the instance that sent it.

A design choice worth noting is how channels are laid out. Publishing to one channel per stream (something like chat:stream:<id>) and subscribing with a single pattern subscription keeps the subscriber code simple. Each instance holds one subscription rather than managing a subscribe and unsubscribe for every stream as viewers come and go.

One more detail matters for correctness: the Redis listener should not write to the hub's client map directly. It should send messages into the same broadcast channel that local messages use, so the single-goroutine guarantee holds.

 Why Pub/Sub and Not Something Heavier

Redis Pub/Sub is fire-and-forget. If a subscriber is disconnected when a message is published, that message is gone for that subscriber. For payments that would be unacceptable. For live chat it is usually fine, for three reasons:

Chat is ephemeral by nature, and a dropped message during a brief blip is rarely noticed.Every message is also persisted to the database, so history is complete even if live delivery isn't.The operational cost is tiny compared with running Kafka or a full message broker.If you later need replay, consumer groups, or delivery guarantees, Redis Streams, NATS JetStream, or Kafka are the natural next steps. Start simple and upgrade when a real requirement forces you to.

 Putting It Together

The full flow looks like this:

Client connects via WebSocket to something like /api/v1/streams/:id/ws, with auth.Connection is upgraded and the client is registered with the local hub for that stream.Client sends a message. The service layer validates it (rate limit, ban check, permissions), persists it to the database for history, then pushes it to the local hub and publishes it to Redis with the instance ID.Other local clients receive it instantly from the hub.Other instances receive it from Redis, see a different instance ID, and broadcast it to their own local clients.

 Things That Bite You in Production

Ordering. Within a single instance, messages are delivered in the order the hub processes them. Across instances there is no global ordering guarantee. Two users on different instances can send messages at nearly the same moment, and viewers may see them in different orders. For most chats this is acceptable, but if it matters, assign ordering on the server using database timestamps or sequence IDs and let clients sort on that.

Authentication and origin checks. WebSocket upgrades bypass a lot of the protections you rely on for normal HTTP requests. Validate the token during the upgrade, check the Origin header, and re-check permissions when bans or role changes happen mid-session, not just at connect time.

Reconnection storms. When an instance restarts, every client it held reconnects at once. Clients should use exponential backoff with jitter so they don't all retry in lockstep and overwhelm the remaining instances.

Heartbeats. Half-open connections are common, especially on mobile. Use WebSocket ping/pong with read deadlines so dead connections get cleaned up rather than lingering in the hub's map and leaking memory.

Message size and rate limits. Cap payload sizes and rate limit per user, for example 5 messages per second. Stream chat gets hot fast, and one spammer can saturate both the hub and Redis.

Observability. Track connected clients per instance, messages published and received per second, dropped slow clients, and Redis publish errors. When chat feels laggy, these numbers tell you whether the problem is the hub, the network, or Redis.

 Lessons Learned

Filter your echoes. The instance ID check is non-negotiable. Without it, you get duplicate messages.Never block the hub. Drop slow clients rather than letting them stall everyone else.Persist for history. WebSockets are ephemeral. Write every message to your database so clients can load history on reconnect.Don't let Redis block chat. If a publish fails, log it and carry on. Local delivery should never depend on Redis being up.Plan for disconnects. Networks drop. Build reconnection with backoff into the client from day one.Know the limits. Pub/Sub doesn't persist messages, and every instance receives every message for the streams it subscribes to. That is fine at moderate scale, but at very high volume you'll want to shard channels or move to a different transport.

 Conclusion

The hybrid in-memory plus Redis approach is a sweet spot for most applications. It keeps the fast path local, scales horizontally with one small dependency, and degrades gracefully when Redis is unavailable. It doesn't overcomplicate your architecture before you need it, and the upgrade path to Streams or a full broker stays open. If you're building real-time features in Go, this pattern is worth stealing.[#architecture](https://www.urbanmind.net/search?tag=architecture) [#backend](https://www.urbanmind.net/search?tag=backend) [#go](https://www.urbanmind.net/search?tag=go) [#systemdesign](https://www.urbanmind.net/search?tag=systemdesign) [#software](https://www.urbanmind.net/search?tag=software) [#coding](https://www.urbanmind.net/search?tag=coding) [#development](https://www.urbanmind.net/search?tag=development) [#engineering](https://www.urbanmind.net/search?tag=engineering) [#inclusive](https://www.urbanmind.net/search?tag=inclusive) [#community](https://www.urbanmind.net/search?tag=community)

💬 Authentication seems simple at first glance. Then you add "remember me", OAuth, 2FA, and proper session revocation, and it gets complicated fast.

Wapi is a live streaming app tailored for African content, with a backend written in Go using Gin. Its auth system covers many production concerns, from token rotation to two-factor login. In this post I'll walk through the pieces, why each one matters, and the mistakes that are easy to make along the way.

 The Token Strategy: Access and Refresh Tokens

Wapi uses the classic dual-token approach. Short-lived access tokens authenticate API requests, and longer-lived refresh tokens obtain new access tokens without forcing the user to log in again.

The login endpoint returns both tokens along with the user profile. When the access token expires, the client calls the refresh endpoint, which issues a new access token and a new refresh token.

That second part is the important one: refresh token rotation. Every time a refresh token is used, it is invalidated and replaced. This limits the damage if a refresh token is stolen, because the thief and the real user can't both keep using the same token.

Rotation also gives you theft detection. If someone presents a refresh token that has already been rotated, one of two things happened: a client retried badly, or a token was copied. Either way, the safe response is to revoke the entire session the token belonged to and force a fresh login.

 JWTs Done Right

JSON Web Tokens are convenient and easy to misuse. A few rules go a long way:

Keep access tokens short-lived. Minutes, not hours. The shorter the lifetime, the smaller the window an attacker has with a stolen token.Sign properly. Use a strong secret (HMAC) or an asymmetric key pair (RSA or ECDSA). Pin the expected signing algorithm when parsing, so a token can't claim a weaker one.Never put sensitive data in the payload. A JWT is signed, not encrypted. Anyone holding the token can read its claims.Validate everything. Check the signature, the expiry (exp), and the issuer and audience where they apply.Store minimal claims. Usually just the user ID, a token ID (jti), and the expiry. Don't bloat the token, since it travels with every request.In a Gin application this lives in middleware. It extracts the Bearer token from the Authorization header, validates it, and attaches the user ID to the request context so downstream handlers never have to parse tokens themselves.

There is one trade-off to be honest about. A pure JWT is stateless, so the server can't "un-issue" it before it expires. That is why access tokens must be short-lived, and why real revocation happens at the refresh token and session level. If you need instant revocation of access tokens, for example after a ban, you can check the token's session ID against a store on each request. That reintroduces state, so it's a deliberate trade of some of JWT's simplicity for control.

 Session Management

Tokens alone aren't enough. Users and the system both need to be able to see and end sessions. Wapi exposes endpoints to list active sessions, revoke a specific session, and revoke all sessions at once.

This matters for several scenarios:

"Sign out of all devices" after a lost phone or a password changeKilling suspicious sessions once a login looks wrongMeeting security expectations that users increasingly take for grantedTo support it, you track each refresh token (or session ID) in the database along with metadata: device or user agent, IP address, creation time, and last-used time. Validating a refresh token then means checking that it exists and hasn't been revoked, and logging out means revoking it. The metadata is what turns a bare list of tokens into something a user can understand, such as "Chrome on Windows, last active two hours ago".

Store a hash of the refresh token rather than the token itself, the same way you would treat a password. If the database leaks, the stored values shouldn't be usable.

 Two-Factor Authentication (TOTP)

Adding 2FA is one of the biggest security upgrades you can make. Wapi implements TOTP (Time-based One-Time Passwords), which works with Google Authenticator, Authy, 1Password, and similar apps.

The flow has four stages:

Setup. An authenticated user requests 2FA setup. The server generates a secret and returns an otpauth:// URI, which the client renders as a QR code. The secret is stored (encrypted) against the user but not yet active.Verification. The user scans the QR code and enters the code their app displays. The server checks it against the stored secret, and only then switches 2FA on. This confirms the user's app is configured correctly before they can lock themselves out.Login with 2FA. When 2FA is enabled, a correct email and password no longer produce tokens. The server returns a short-lived challenge instead, and the user completes login by submitting a TOTP code. Only then are access and refresh tokens issued.Disabling. Turning 2FA off requires re-authentication, so someone with a briefly unattended session can't quietly weaken the account.Two details deserve attention. First, the login challenge should be a single-purpose credential: short expiry, usable only to complete 2FA, and never accepted as an access token. Second, 2FA verification needs its own strict rate limit. A six-digit code has only a million possibilities, and brute-forcing that is realistic if attempts are unthrottled.

Finally, plan for account recovery. Users lose phones, so you'll want backup codes, generated at setup, stored hashed, and single-use.

 OAuth 2.0 (Google and Facebook)

Social login is convenient for users and has its own pitfalls. Wapi uses the standard authorization code flow:

The client hits the server's login endpoint for a provider, which redirects to the provider's authorization page.The user authenticates with the provider and consents.The provider redirects back to the server's callback endpoint with an authorization code.The server exchanges the code for tokens with the provider and fetches the user's profile.The server finds or creates a local account linked to that provider identity.The server issues its own access and refresh tokens.Step 6 is where Wapi does something smart. Instead of putting tokens in the redirect URL, it redirects the browser back to the frontend with a short-lived one-time code, and the frontend exchanges that code for tokens through a separate endpoint. URLs end up in browser history, server logs, and Referer headers, so tokens don't belong there. A code that is single-use and expires in seconds is a much safer thing to leak.

A few OAuth details are easy to miss:

Validate the state parameter to protect against cross-site request forgery on the callback.Use PKCE where the provider supports it.Be careful when linking accounts by email. Only auto-link to an existing local account if the provider confirms the email is verified. Otherwise an attacker can register at a provider with someone else's address and take over their account.

 Rate Limiting for Abuse Prevention

Auth endpoints are prime targets for credential stuffing and brute-force attacks. Wapi applies different limits depending on the endpoint:

Endpoint typeLimitKeyed bySignup, login, password reset10 per minuteIPOAuth initiation5 per minuteIP2FA verification (suggested)Stricter than login, for example 5 attempts per 15 minutesIP and user or session
The limiter is built on golang.org/x/time/rate, with buckets stored per key. When a limit is hit, the API returns 429 Too Many Requests with a clear error code so clients can back off gracefully.

An in-memory limiter is fine for a single instance, but note what happens when you scale out. Each instance counts separately, so your effective limit is multiplied by the number of instances. When you run more than one, move the counters to Redis, using a sliding window or token bucket, so every instance shares the same view. Also remember that IP-based limits are blunt: users behind a shared NAT share a bucket, and attackers rotate IPs. That matters even more for a mobile-heavy audience, where carrier-grade NAT can put many real users behind one IP. That is why the 2FA limit also keys on the user or session.

 Security Best Practices to Keep in Mind

Password hashing. Never store plaintext passwords. Use bcrypt, argon2, or scrypt with a sensible cost factor, and raise it over time as hardware improves.Email verification. Verify addresses before allowing sensitive actions.Password reset. Use time-limited, single-use tokens delivered by email, and invalidate existing sessions when a reset completes.Account enumeration. Return the same response whether or not an email exists, for login errors and for password reset requests.CORS. Lock allowed origins down to the ones you actually use.Secure headers. Add standard security headers in production.Token storage on the client. HttpOnly, Secure, SameSite cookies protect tokens from theft via XSS in a way localStorage can't. The trade-off is that cookie-based auth needs CSRF protection, which SameSite helps with. If you send tokens in an Authorization header instead, keep them in memory and accept the refresh-on-reload cost.

 Putting It All Together

A robust auth system isn't about implementing every feature at once. It's about layering defenses. Start with solid password authentication and short-lived JWTs. Add refresh token rotation and session management so users can end sessions remotely. Layer on 2FA for accounts that matter, add OAuth for convenience, and wrap everything in rate limiting.

What stands out in Wapi's implementation is that these pieces are wired up and work together rather than existing as isolated features. The routes are organized logically, the middleware is reusable, and each flow closes the gaps the previous layer leaves open.
